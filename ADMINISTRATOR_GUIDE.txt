IDS LAB - ADMINISTRATOR GUIDE (WIREGUARD)
========================================

Lab administrator contact: mwestermeyer@udec.cl

Deployment: existing public WireGuard server, dedicated outbound lab
peer, individual student peers, and SSH/X2Go/XFCE on the GPU lab PC.

Fixed lab IPv4: 10.8.0.100 (X2Go and SFTP, TCP 22).
Public WireGuard endpoint: 152.74.19.95:10275/UDP.
Private lab profile: ~/IDS_remote/IDS_5090.conf, excluded from Git.
Verify the live interface and student access after changes; the saved address
does not by itself prove a working connection. Keep local access during changes.

1. PREPARE THE LAB NOW
----------------------
On Pop!_OS/Ubuntu 22.04/24.04, in a normal administrator terminal:

    cd ~/IDS_remote
    sudo bash install_wireguard.sh --prepare

This installs dependencies. It does not install a profile, start WireGuard or
change the student SSH network. Package installation may start distribution
SSH/X2Go services. No NVIDIA/CUDA/PyTorch changes are made.

WIREGUARD_DEPLOYMENT.md contains the full deployment, topology, firewall and
migration procedure. WireGuard uses UDP: verify outbound reachability to the
real public endpoint from the lab. No lab router port forwarding is required.

2. INFORMATION REQUIRED BEFORE INSTALLATION
-------------------------------------------
In the public server's WireGuard GUI, create a dedicated lab peer and export
its .conf privately. Create a separate peer/profile for every student device.
The lab installers do not require public-server shell access. Record:

    Public server endpoint/UDP port: 152.74.19.95:10275/UDP
    Lab VPN IP: 10.8.0.100 (reserve exclusively for the GPU PC)
    Student VPN source CIDR seen by lab SSH: ___________
    Current lab interface name: IDS_5090 (from IDS_5090.conf)
    Student peer provisioning/revocation contact: ______

Do not reuse a personal or student profile for the lab. Every device needs a
unique key/address registered on the public server. Transfer completed .conf
files privately, outside Git; never share the lab's private key with students.
wireguard/*.conf.example files contain placeholders for review, not credentials.

The public server must permit forwarding between student and lab peers, with
return traffic. Configure matching AllowedIPs for each peer and the lab's reply
route. Coordinate IP forwarding and firewall rules with its administrator.
If the hub applies SNAT, the SSH source CIDR must match the translated source,
not the original student addresses. The lab installer cannot configure the hub. If the GUI has no forwarding or
firewall controls, ask its administrator to verify existing rules. Opening the
WireGuard endpoint port alone does not prove student-to-lab reachability.

3. CONNECT THE CURRENT LAB PROFILE
-----------------------------------
The private IDS_5090.conf uses Address=10.8.0.100/32. Keep this address consistent
with the lab peer in the public GUI. Never assign 10.8.0.100 to a student.
Use the current profile directly from a local administrator terminal:

    cd ~/IDS_remote
    chmod 600 IDS_5090.conf
    sudo wg-quick up ./IDS_5090.conf

If already active, do not run up again. To reload a changed profile:

    sudo wg-quick down ./IDS_5090.conf
    sudo wg-quick up ./IDS_5090.conf

These steps interrupt current VPN sessions; perform them locally.
The profile includes ::/0, so IPv6 traffic uses the VPN. Its DNS settings need
working resolvconf integration. Keep PersistentKeepalive=25 for idle reachability.
The installer's --check-config/--install path rejects default routes; the current
reviewed profile is started with standard wg-quick instead. Templates show the
IPv4-only explicit-route alternative, not a replacement for the private profile.

4. VERIFY AND PREPARE SSH/X2GO
------------------------------
    ip -4 address show dev IDS_5090
    sudo wg show IDS_5090

Expect 10.8.0.100/32 on the interface and a recent handshake. Seeing a peer in
the public GUI or seeing an active interface does not prove student access.
Prepare SSH/X2Go for the configured VPN source subnet:

    sudo bash -c 'source ./lib/remote_access.sh; configure_student_network 10.8.0.0/24'

This backs up/migrates only unchanged installer-managed SSH snippets and validates
before reload. Custom policies need review. If the server uses SNAT, use the
actual source CIDR seen by the lab instead. Test student -> 10.8.0.100:22 from
outside the lab LAN. Keep current administrative access while changing policy.

The lab firewall must allow the actual student source CIDR to 10.8.0.100
on TCP 22 over this WireGuard interface. Preserve administrative access.
The public hub needs a forwarding rule; allowing SSH to the hub itself is not
enough. Isolate students from each other according to the lab's policy.

Diagnostics:
    sudo systemctl status ssh x2goserver --no-pager
    sudo wg show IDS_5090
    sudo journalctl -u ssh -u x2goserver -n 50 --no-pager
    ip -brief address
    ip route
    sudo sshd -t

To stop the current manually started tunnel:
    sudo wg-quick down ./IDS_5090.conf

Stopping it does not restore old SSH rules or remove the private profile. Do
not publish full profiles, wg showconf output or wg dump output: they may expose
private/preshared keys. Do not stop unrelated VPN services without checking users.

5. CREATE AND MANAGE LINUX ACCOUNTS ON THE LAB
---------------------------------------------
    cp usuarios.example.txt usuarios.txt
    # Edit usuarios.txt: one real username per line; no passwords/emails.
    bash usr_mgr.sh --import usuarios.txt --dry-run
    sudo bash usr_mgr.sh --import usuarios.txt

Usernames start with a lowercase letter and use 3-31 lowercase letters/digits,
underscores or hyphens. Blank lines, # comments, CRLF and
duplicate names are supported. Preview validates the list only. Real import
checks conflicts before creating accounts and skips existing managed accounts.
Skipped accounts are not reactivated and their passwords are not reset.

Accounts have private HOME and no sudo. The default initial password is the
username in lowercase without spaces (student01 -> student01), for both the
interactive add option and TXT imports. Usernames already require lowercase
and no spaces. This predictable password can be changed by the student using
passwd; existing account passwords are not reset by this change.
Import passwords are stored in a
private credenciales-*.tsv file under /root/credenciales-alumnos/, with columns
usuario, contraseña, estado. Inspect the printed file path with sudo less. Each user gets an initial password row and,
if provisioning succeeds, a separate creado completion row. A pending record
alone does not prove the account was created. Deliver only each user's own
password privately; never distribute the class TSV.

The same student/device also needs its own WireGuard peer profile from the VPN
administrator. usr_mgr.sh does not generate WireGuard keys or register peers.

List managed students without opening the menu:
    sudo bash usr_mgr.sh --list

Listing includes primary and supplementary members of alumnosvpn, once each.
Unavailable password status is reported without interrupting the list. After
updating the script, exit any already-open manager and start it again.

Interactive account manager:
    sudo bash usr_mgr.sh

Spanish menu: 1 add, 2 list, 3 suspend, 4 reactivate, 5 delete/archive,
6 import TXT, 0 exit. Deletion requires typing ELIMINAR USERNAME exactly.
Homes are archived under /root/archivos-alumnos/. To reset a Linux password:
    sudo passwd ACTUAL_USERNAME

The original import TSV is not updated after password changes. Suspension
terminates the student's Linux sessions/processes. Withdrawal also requires
removing the student's WireGuard public-key peer on the public server, using
the WireGuard GUI; save the change so it persists. Removing a VPN peer alone
does not terminate existing training processes on the lab.

6. HANDOVER AND GPU VALIDATION
------------------------------
Provide each student only their own VPN profile and Linux credentials, the
fixed lab VPN IP 10.8.0.100, SSH port 22, session XFCE, support contact and GPU schedule.
Give them CLIENT_GUIDE.txt plus a trusted SSH host-key fingerprint:

    sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

For a different negotiated host-key type, supply its corresponding fingerprint.
Test two students outside the LAN with their own HOME/DISPLAY, SFTP and X2Go.
Run nvidia-smi inside their sessions. Then, in the course Python environment:

    python -c "import torch; assert torch.cuda.is_available(); x=torch.randn(256,256,device='cuda',requires_grad=True); (x@x).square().mean().backward(); torch.cuda.synchronize(); print(torch.cuda.get_device_name(0))"

PyTorch must already be installed in that environment. If nvidia-smi fails on
the host, resolve driver/device access before announcing GPU training. Check
RTX 5090 compatibility in the actual framework; the installers do not do it.
There are no GPU/VRAM/RAM/disk quotas or scheduling: coordinate class usage.
Keep the lab powered on, avoid automatic sleep during class, and back up student
data according to the course's policy.

Root-free tests (account mutations are simulated):
    python3 -m unittest discover -s tests -v
